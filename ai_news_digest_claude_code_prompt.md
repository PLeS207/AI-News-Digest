## 2. Реальная задача и границы MVP

Создай персонального Telegram-бота AI News Digest. По запросу он собирает свежие публикации из 2–3 настроенных RSS-источников и готовит короткий дайджест с учётом сохранённых интересов пользователя.

Начальные интересы: AI agents, MCP, LLM, AWS Bedrock и инструменты для разработчиков. Язык ответа по умолчанию — русский, размер дайджеста — до 5 новостей, период по умолчанию — последние 72 часа.

Примеры сообщений:
- «Запомни: меня интересуют AI agents, MCP и AWS Bedrock. Пиши по-русски, максимум 3 новости».
- «Подготовь дайджест AI-новостей за последние 72 часа».
- «Какие интересы и настройки ты сохранил?»
- «Покажи последний дайджест».
- «Собери ещё один дайджест, пропусти уже отправленные новости».

MVP работает по запросу, обслуживает одного разрешённого Telegram-пользователя и использует один bot token. Настройки периода, лимита и источников должны быть простыми и документированными.

Каждая новость содержит заголовок, дату публикации, 2–3 предложения саммари, короткое возможное применение для Cloud Architect / DevOps и исходную ссылку. Возможное применение обозначай как вывод агента. Саммари основывай на доступном тексте RSS; не создавай впечатление, что полная статья прочитана, если это не так.

## 3. Стек и архитектура

Используй Python, официальный A2A Python SDK, Anthropic Python SDK, python-telegram-bot, RSS-парсер, SQLite и простой read-only Streamlit dashboard.

Перед реализацией проверь актуальные официальные документации SDK и совместимость выбранных версий. Зафиксируй проверенные версии зависимостей и версию A2A, которую реализует проект. Не выдумывай названия методов SDK и пути endpoints.

Достаточно трёх сервисов в Docker Compose:
- app: Telegram polling и агент Editor / Coordinator, включая A2A client;
- researcher: отдельный процесс с A2A server и агентом Researcher;
- dashboard: просмотр реальных событий обоих агентов.

Telegram использует long polling. Исследователь доступен app по внутренней сети Compose. Dashboard публикуется на localhost. SQLite и трассы сохраняются в постоянных volumes. Состояние Editor и Researcher храни раздельно; dashboard получает read-only доступ к их трассам.

Оба агента действительно вызывают LLM. Модель задай через ANTHROPIC_MODEL, ключ — через ANTHROPIC_API_KEY. Проверь доступность настроенной модели при live smoke test. Авторизацию CLI для написания кода не считай автоматически credentials приложения.

Минимальный цикл агента: LLM получает запрос и разрешённые tools, запрашивает нужные вызовы, получает результаты и формирует ответ. Ограничь число итераций и объём входных данных; для MVP достаточно до 4 LLM-итераций и до 8 tool calls на агента за запрос.

## 4. Роли и реальные границы доступа

Researcher:
- Имеет собственный system prompt и tool для получения RSS по source_id из конфигурации.
- Получает период, интересы, лимит и список уже доставленных URL через A2A.
- Получает материалы, с помощью LLM отбирает релевантные и возвращает структурированный результат с evidence и ссылками.
- Имеет доступ к RSS tool и собственным trace-событиям.
- Не имеет tools для Telegram, изменения пользовательских настроек или чтения базы памяти Editor.

Editor / Coordinator:
- Имеет собственный system prompt.
- Общается с пользователем через Telegram-адаптер приложения.
- Использует tools чтения/сохранения настроек, истории дайджестов и вызова Researcher через A2A.
- При запросе дайджеста обязательно обращается к Researcher и использует его фактический результат.
- Проверяет ссылки и составляет окончательный дайджест, сохраняя настройки и историю.
- Не имеет RSS/web-fetch tool.

Разграничение реализуй в коде: отдельные tool registries / allowlists и проверки при dispatch. Одних фраз в system prompt недостаточно. Не предоставляй агентам общий shell, доступ к произвольным файлам или секретам.

RSS tool должен принимать только настроенные source_id. Пользовательские сообщения и тексты источников являются данными, а не инструкциями для расширения прав.

## 5. A2A и контракт результата

Официальные reference:
- https://a2a-protocol.org/latest/
- https://github.com/a2aproject/a2a-python

Researcher должен публиковать Agent Card и принимать задачи через поддерживаемый официальным SDK A2A transport. Editor использует A2A client, обнаруживает Researcher и отправляет запрос. Достаточно одного направления задач: Editor → Researcher → результат Editor.

Передавай типизированные данные и валидируй их, например Pydantic-моделями. Результат исследования должен включать:
- request_id / trace_id;
- запрошенный период и фактическое время сбора;
- articles: source_id, title, url, published_at, available_excerpt, relevance_reason;
- ошибки отдельных источников и признаки неполного результата.

В трассе должны быть видны discovery, отправка задачи, идентификатор A2A-задачи, её статус и получение результата. Предусмотри timeout и ограниченный retry для временной ошибки; исключи бесконечные циклы.

Если Researcher недоступен, Editor сообщает об ошибке и не подменяет результат выдуманными новостями. Не называй взаимодействие A2A только на основании имени функции.

## 6. RSS-источники и качество данных

Начальные кандидаты, доступность которых нужно проверить:
- OpenAI News: https://openai.com/news/rss.xml
- Hugging Face Blog: https://huggingface.co/blog/feed.xml
- AWS What's New: https://aws.amazon.com/about-aws/whats-new/recent/feed/

Достаточно двух работающих источников. Если кандидат недоступен или не является RSS/Atom, отметь это в README и конфигурации. AWS-ленту фильтруй по интересам, поскольку она содержит много новостей вне AI.

Список источников вынеси в конфигурацию. Используй HTTP timeouts, ограничение размера ответа и числа статей; не обходи полные сайты. Очисти HTML и ограничь длину excerpt перед передачей модели. Для одного запроса достаточно до 30 последних записей суммарно.

Даты храни в UTC и корректно фильтруй по временному окну. Публикации без определяемой даты не выдавай за новости выбранного периода. При отсутствии релевантных публикаций ответь об этом. Не заполняй лимит выдуманными или устаревшими новостями.

Удаляй дубли по canonical URL. Удаляй tracking-параметры вроде utm_*, сохраняя параметры, определяющие саму статью. Ссылки итогового дайджеста должны присутствовать в материалах Researcher.

Добавь небольшой набор локальных RSS fixtures с фиксируемым тестовым временем: offline-проверки должны быть воспроизводимыми.

## 7. Persistent memory

Editor использует SQLite для сохранения:
- интересов, языка и размера дайджеста;
- последнего и предыдущих дайджестов;
- URL новостей, успешно доставленных пользователю.

Обработай явное сообщение «Запомни...» и запрос на чтение сохранённых настроек. При каждом новом запросе загружай нужную память из базы. После перезапуска это должны быть те же сохранённые значения, а не восстановление из старого prompt или transcript.

Добавь /new: очистка краткоживущего контекста беседы при сохранении persistent memory. В README покажи проверку с настройкой значения, отличающегося от default, например лимита 2 новостей.

Помечай статьи доставленными после успешной отправки Telegram. При частичной отправке большого дайджеста учитывай фактическую доставку частей; не отмечай неотправленные статьи как доставленные. Историю и настройки не коммить. Researcher не получает прямой доступ к этой базе.

## 8. Observability

Собирай реальные события в структурированные trace-файлы или эквивалентное небольшое хранилище. Инструментируй вызовы в коде, а не проси модель придумывать записи о работе.

В dashboard нужны:
- список запусков: время, trace_id, статус и длительность;
- timeline выбранного запуска с ролью агента;
- LLM calls, tool calls, A2A request/result и task_id;
- статусы started / completed / failed и ошибки;
- memory read/write и подтверждение отправки ответа;
- краткие входы/выходы с ограничением длины.

Объедини события двух процессов по trace_id. Достаточно простого read-only экрана с обновлением данных; сложный frontend не нужен. Если доступны токены usage от provider, покажи их, но не выдумывай метрики.

Не логируй API keys, bot token, Authorization headers или приватные идентификаторы пользователя в публичные примеры. Trace-файлы остаются локальными, игнорируются Git и переживают перезапуск.

## 10. Проверки и сценарий демонстрации

Автоматические offline-проверки с mocked LLM / Telegram:
- RSS parsing, фильтрация по времени, canonical URL и дубли.
- Сохранение и повторная загрузка настроек из одной SQLite после пересоздания приложения.
- Невозможность вызвать tool другой роли.
- Реальный локальный A2A server/client round trip через официальный SDK, включая discovery и валидацию результата.
- Ошибка RSS-источника и недоступность Researcher.
- Отказ неразрешённому Telegram-пользователю.
- Пометка доставленных URL только после успешной отправки.

Для offline A2A-проверки допускается fake LLM; транспорт и клиент должны быть настоящими. Offline-проверка не доказывает работу модели или Telegram в live.

При наличии credentials выполни и запиши фактический результат live demo:
1. Установить интересы и лимит 2 новости через Telegram.
2. Получить дайджест из настоящих RSS.
3. В dashboard показать обе роли, RSS tool, A2A task и успешную доставку.
4. Перезапустить app и researcher без удаления volumes.
5. Начать новую беседу через /new.
6. Спросить сохранённые настройки: лимит 2 должен загрузиться из базы.
7. Запросить новый дайджест: уже доставленные URL пропускаются.
8. Показать контролируемую ошибку Researcher и соответствующий failed trace.
